# 도메인 설계

> 기준: 노션 기능명세서(각 파트 공유 내용 정리 → 기능 명세서), 아이디어 구체화 문서, 와이어프레임·유저 플로우 V0.2 (11/14)
> 새 기능을 만들기 전에 **이 문서에서 어느 도메인에 속하는지** 먼저 확인하세요.

## 1. 서비스 한 줄 요약

내가 바꿀 수 없는 기다림(합격 발표, 답장)을 **2D 간이역 대기실에서 다른 승객과 함께 보내는 서비스**입니다.
사용자는 승차권을 받고 대기실에 앉아 있다가, 열차가 지날 때마다 털실을 받고, 기다림이 끝나면 담요 조각 1칸을 받습니다.

```
시작화면 → 입구 → 대기실 선택 → 상태 칩 선택 → 승차권 발급 → 자동 착석
→ 함께 기다리기 (열차가 지날 때마다 털실, 털실 톡톡은 선택)
→ 기다림 종료 → 담요 조각 선물 → 저장 → 마이 양의 내 담요
```

## 2. 도메인 한눈에 보기

| 패키지 | 한글 이름 | 맡는 것 | 저장 | 담당 |
|---|---|---|---|---|
| `user` | 계정 | 닉네임+PIN 가입·로그인·로그아웃, 담요 공개 설정 | DB | 상진 |
| `room` | 대기실 정보 | 방 목록, 슬로건·문구, 상황 칩, NPC, 가상 승객 정의, 도안 | DB (시드 데이터, 시작 시 메모리에 로드) | 하빈 |
| `ticket` | 승차권 | 기다림 한 건의 시작부터 종료까지, 열차·털실 계산, 털실 톡톡, 전광판 통계 | DB | 환희 |
| `blanket` | 담요 | 계정 담요 조각, 내 담요, 임시 조각을 계정으로 옮기기, 공개 카드 | DB (임시 조각은 브라우저) | 상진 |
| `realtime` | 실시간 대기실 | 접속 승객, 좌석, 존재감, 방송, 리액션, 전광판 송출 | **메모리만** | 환희 |
| `global` | 공통 | 설정, 보안(토큰 발급·검증, 현재 사용자), 예외, 공통 응답 | — | 환희 |

- `global`은 모두가 쓰는 코드라 **담당자(환희)만 수정**합니다. 필요한 게 있으면 요청해 주세요.
- 다른 도메인의 기능이 필요하면 그 도메인 담당자와 **메서드 이름과 형태를 먼저 맞추고** 개발합니다. 예: `ticket`(환희)이 종료 때 `blanket`(상진)의 조각 생성 메서드를 호출

### 관계

```
room ─── 1:N ─── ticket (털실 톡톡은 ticket 컬럼으로 포함)
                   │
user ─── 0..1:N ───┤   비로그인 승차권은 user 없이 guestToken으로 구분
                   │
                   └─── 1:0..1 ─── blanketPiece ─── N:1 ─── user
                                   (계정 조각만 DB에 있음)

realtime: DB 관계 없음. 접속 중인 승객을 ticket 기준으로 메모리에 들고 있음
```

### 서비스 호출 방향

```
realtime ──→ ticket ──→ blanket
   │            │
   └──→ room ←──┘          user ←── ticket, blanket (소유자 확인)
```

- 화살표 반대 방향으로는 호출하지 않습니다 (순환 참조 금지).
- 예: 기다림 종료는 `TicketService.end()`가 `BlanketService.createPiece()`를 호출합니다. blanket이 ticket을 호출하지 않습니다.

## 3. 용어집

**한 개념에는 한 단어만 씁니다.** 클래스, 변수, API 경로 모두 이 표를 따릅니다.

| 명세서 용어 | 코드 이름 | 설명 |
|---|---|---|
| 승차권, 기다림 | `Ticket` | 둘 다 Ticket입니다. `Waiting`은 쓰지 않습니다 |
| 승차권 번호 | `ticketNumber` | "104번 두근두근한 양"의 104 |
| 대기실 호칭 | `displayName` | 승차권 번호 + 상태 칩 호칭형 + '양'. 예: 104번 두근두근한 양. 상태 칩이 없으면 104번 양 |
| 대기실(방) | `Room` | 결과발표 / 읽씹 / 결선 |
| 상황 칩 | `SituationChip` | 방마다 다름 |
| 상태 칩 | `MoodChip` | 공통 12개 (와이어프레임 S03 기준). `StatusChip`은 `TicketStatus`와 헷갈려서 쓰지 않습니다 |
| 열차 | `Train` | 1시간마다 지나감. 저장하지 않고 계산 |
| 털실 한 올 | `Yarn` | 열차 1대 = 털실 1올. 저장하지 않고 계산 |
| 털실 톡톡 | `Knitting` | 탭으로 도안을 채우는 미니 콘텐츠. 서버는 도안 코드와 전달 시각만 가짐 |
| 도안 | `Pattern` | 조각의 무늬 |
| 담요 조각 | `BlanketPiece` | `Piece`만 쓰지 않습니다 |
| 종료 사유 | `EndReason` | `ANSWERED` 답이 왔어요 / `UNEXPECTED` 기대와 달랐어요 / `LET_GO` 내려놓을래요 |
| 방송 | `Broadcast` | 상황 칩 + 상태 칩 조합 |
| 리액션 | `Reaction` | `NOD` 끄덕임 / `AWW` 짠함 |
| 승객 | `Passenger` | 지금 대기실에 접속한 양. `realtime`에서만 사용 |
| 가상 승객 | `VirtualPassenger` | 시연용으로 자동 방송하는 승객 |
| NPC | `Npc` | 방마다 1명, 조용히 앉아만 있음. 방송·리액션 불참 |
| 계정 | `User` | 닉네임+PIN으로 가입한 계정만. 비로그인 사용자는 User가 아닙니다 |
| 게스트 토큰 | `guestToken` | 비로그인 사용자의 승차권 소유 확인용. 브라우저가 보관 |
| 계정 닉네임 | `nickname` | 본인만 보는 이름 (마이 양). 대기실에는 공개하지 않습니다 |

## 4. 도메인별 상세

### 4-1. `user` 계정

| 기능 ID | 내용 |
|---|---|
| MY-01 | 간이 회원가입: 닉네임 + PIN 4자리 + PIN 확인 |
| MY-09 | 기존 계정 로그인: 닉네임 + PIN |
| MY-10 | 로그아웃 (서버 데이터는 유지) |
| MY-04 | 담요 공개 설정 (기본 비공개, 로그인 사용자만) |
| SV-01 | 로그인 상태 판별 |

- 주요 데이터: `User` (닉네임, PIN 해시, 공개 여부, PIN 실패 횟수, 잠금 해제 시각)
- **User는 가입한 계정만**입니다. 로그인하지 않은 사람은 User를 만들지 않습니다.
- **닉네임**: 최대 12자, **중복 불가** (닉네임으로 로그인하기 때문). 마이 양에서 본인에게만 보이고 대기실에는 공개하지 않습니다.
- **PIN**: 숫자 4자리. `PasswordEncoder`로 **해시해서 저장**하고, **틀린 횟수를 제한**합니다 (예: 5번 실패 시 잠시 잠금). PIN 분실 시 복구는 MVP에서 지원하지 않습니다.
- PIN은 가입·로그인 때만 씁니다. 대기실 입장 때는 묻지 않습니다.
- **로그아웃**은 프론트가 저장된 로그인 토큰을 지우는 것으로 처리합니다. 서버에서 토큰을 강제로 무효화하지 않습니다.
- 가입·로그인에 성공하면 `blanket`의 "임시 조각 옮기기"를 이어서 호출합니다 (4-4 참고).
- 토큰 발급·검증과 "현재 사용자 꺼내기"는 `global/security`가 맡고, `user`는 그걸 가져다 씁니다.

### 4-2. `room` 대기실 정보

| 기능 ID | 내용 |
|---|---|
| ON-02 | 대기실 목록 |
| RM-01 | 방 슬로건·문구 (입장, 열차 통과, 종료 3종, 회고 질문 2개) |
| RM-03, RM-04 | NPC 정보, 공감 문구(P1) |
| RM-05 | 가상 승객 정의 |
| YT-01 | 도안 목록 (랜덤 배정용) |
| SF-02 | 칩 목록 고정 (자유 입력 없음) |

- 주요 데이터: `Room`, `SituationChip`, `Npc`, `VirtualPassenger`, `Pattern`
- `MoodChip`(상태 칩 12개)은 모든 방 공통이라 **enum**으로 둡니다. 목록은 **와이어프레임 S03** 기준이고, 문구가 이미 호칭형이라 그대로 대기실 호칭에 씁니다.

  | enum | 문구 | enum | 문구 | enum | 문구 |
  |---|---|---|---|---|---|
  | `NERVOUS` | 조마조마한 | `BLANK` | 멍한 | `COMPOSED` | 담담한 |
  | `FLUTTERING` | 두근두근한 | `TIRED` | 지친 | `RELIEVED` | 한숨 돌린 |
  | `RESTLESS` | 마음이 바쁜 | `CALM` | 고요한 | `EXCITED_ANXIOUS` | 설레고 불안한 |
  | `ANXIOUS` | 불안한 | `RELAXED` | 느긋한 | `COMPLICATED` | 복잡한 |

- 종료 문구 중 "기대와 달랐어요"는 문서에 없어서 백엔드가 임시로 정하고, 발표 전 어휘 검수(SF-02) 때 기획이 확인합니다.
- 가상 승객은 방마다 2명, 칩 조합은 그 방의 칩에서 랜덤으로 고릅니다.
- 대기실은 결과발표 / 읽씹 / **간지톤 결선** 3개입니다.
- 사용자가 바꾸는 데이터가 아닙니다. 시드 데이터로 넣고 서버 시작 시 메모리에 올려서 요청마다 DB를 조회하지 않습니다.

### 4-3. `ticket` 승차권 (중심 도메인)

| 기능 ID | 내용 |
|---|---|
| ON-03, ON-04 | 상태 칩 선택(선택 사항), 승차권 발급, 대기실 호칭 생성 |
| TR-02, TR-04 | 털실 지급, 지나간 열차 수 |
| YT-03, YT-04, YT-05 | 털실 톡톡 진행, 역장에게 전달, 미참여 시 기본 조각 |
| EN-01 ~ EN-03 | 내려놓기, 종료 사유 선택, 회고 질문 |
| BR-04 | 전광판 "도착 N건 / 내려놓음 N건" 집계 |

- 주요 데이터: `Ticket` (승차권 번호, 방, 소유 계정(nullable), 게스트 토큰, 상태 칩, 상태, 시작·종료 시각, 종료 사유, 도안 코드, 털실 톡톡 전달 시각, 계정으로 옮긴 여부)
- **소유자 구분**
  - 로그인 상태에서 발급: `userId`로 소유
  - 비로그인 상태에서 발급: 서버가 `guestToken`을 만들어 응답에 넣고, 브라우저가 보관합니다. 이후 요청은 이 토큰으로 본인 확인
  - 비로그인이어도 **Ticket은 서버에 저장합니다.** 실시간 대기실, 전광판 통계, 그리고 나중에 계정으로 옮길 때 기록을 검증하는 데 필요하기 때문입니다.
- **대기실 호칭**: `{승차권 번호}번 {상태 칩 문구} 양` (예: 104번 두근두근한 양). 상태 칩이 없으면 `{승차권 번호}번 양`. 방송에서 상태 칩을 고르면 그 칩으로 바뀝니다.
- 상태: `WAITING` → `ENDED`. **이어서 재개는 없습니다.** 다시 기다리려면 새 Ticket을 만듭니다.
- **승차권 번호는 대기실마다 1번부터 순번**으로 매기고 리셋하지 않습니다. 예: 결과발표 방 104번 양
- **저장하지 않고 계산하는 값**
  - 지나간 열차 수 = (종료 시각 또는 현재 - 시작 시각) × 가속 배율 ÷ 1시간
  - 털실 수 = 지나간 열차 수
  - 1시간을 몇 초로 줄일지는 **환경변수**로 둡니다 (기본값: 1시간 = 15초). 첫 열차는 입장 10초 안에 지나가게 합니다
- **털실 톡톡은 서버가 거의 하는 일이 없습니다.**
  - 승차권 발급 때 도안을 랜덤으로 정해 응답에 넣습니다 (YT-01).
  - 탭, 픽셀 채우기, 탭 횟수, 도안 크기는 **전부 프론트**가 처리합니다. 서버는 탭 횟수를 받지도 저장하지도 않습니다.
  - "역장에게 전달"(YT-04)은 body 없는 API 하나입니다. 내 승차권인지, 진행 중인지, 털실이 1개 이상인지 확인하고 전달 시각만 기록합니다. 새로고침해도 털실 보따리 아이콘이 남게 하기 위해서입니다.
  - 참여 여부와 관계없이 조각에는 **발급 때 정한 도안**이 들어가고, 모양은 항상 완성본입니다 (YT-05).
- 전광판 통계는 **종료 사유 3가지를 각각** 세서 내려줍니다 (`ANSWERED`, `UNEXPECTED`, `LET_GO`). 화면에 어떻게 묶어 보여 줄지는 프론트가 정합니다.
- 통계는 **전체 합산만** 제공합니다 (방 단위 통계 없음). 종료 때마다 메모리 카운터를 올리고, 서버 시작 시에만 DB에서 집계합니다.
- 회고 질문 답변(EN-03)은 **저장하지 않습니다** (다시 보여 주는 곳이 없음). 기획 답에 따라 바뀔 수 있습니다.

### 4-4. `blanket` 담요

| 기능 ID | 내용 |
|---|---|
| EN-04, EN-05 | 담요 조각 생성, 뒷면 기록 층 |
| SV-01 ~ SV-05 | 로그인 상태면 자동 저장 / 아니면 계정 저장 여부 선택 / 임시 보관 |
| MY-02, MY-03 | 내 담요, 조각 상세 (앞면·뒷면) |
| MY-05 | 대기실에서 승객 탭 시 공개 카드 |
| MY-08 | 임시 조각을 계정으로 옮기기 |

- 주요 데이터: `BlanketPiece` (Ticket 1:1, 소유 계정, 도안, 뒷면 기록 층). **계정 조각만 DB에 저장합니다.**
- **저장 위치**
  - 로그인 상태에서 종료: 서버가 조각을 만들어 계정에 저장합니다 (SV-01 자동 저장).
  - 비로그인 상태에서 종료: 서버는 조각 정보를 **응답으로만 주고 저장하지 않습니다.** 프론트가 브라우저에 임시 저장합니다 (SV-04).
- **임시 조각을 계정으로 옮기기** (가입·로그인 직후, MY-08)
  - 브라우저는 조각 내용이 아니라 **승차권 ID 목록 + 게스트 토큰**만 보냅니다.
  - 서버는 각 Ticket이 그 게스트 토큰 소유인지, 종료됐는지, 이미 옮긴 적이 없는지 확인한 뒤, **서버의 Ticket 기록으로 조각을 다시 만들어** 계정에 저장합니다.
  - 브라우저가 보낸 조각 내용(승차권 번호, 열차 수, 종료 표식 등)은 믿지 않습니다. 브라우저 데이터는 사용자가 고칠 수 있기 때문입니다.
  - 옮긴 Ticket은 소유 계정을 채우고 "옮김"으로 표시해서 다시 옮길 수 없게 합니다.
- **뒷면 기록 층**(승차권 번호, 기다림 이름, 지나간 열차 수, 종료 표식)은 조각을 만들 때 값을 복사해 두고 **이후에 바꾸지 않습니다.**
- **기다림 이름** = 마지막으로 방송한 상황 칩의 문구. 방송을 한 번도 안 했으면 방 이름.
- 종료 사유와 관계없이 **조각은 항상 1칸**입니다.
- 공개 카드에는 **종료 표식과 닉네임을 넣지 않습니다** (민감 정보는 본인만).

### 4-5. `realtime` 실시간 대기실

| 기능 ID | 내용 |
|---|---|
| ON-05 | 자동 착석 (좌석 배정) |
| RM-02 | 존재감 표시 (머문 시간, 상태 칩) |
| BR-01 | 조합형 방송 (30초 쿨다운) |
| — | 대기실 호칭 표시 (방송 문장, 승객 카드) |
| BR-02 | 전광판 송출 (15초 노출, 순서대로 전환) |
| BR-03 | 1초 리액션 (즉시 전파, 알림 없음) |
| RM-05 | 가상 승객 자동 방송 (스케줄러) |

- **DB에 저장하지 않습니다.** 접속 승객, 좌석, 방송 대기열, 쿨다운 모두 메모리에 있습니다. 서버를 재시작하면 사라지고, 다시 접속하면 복구됩니다.
- 방송·리액션은 다시 조회하는 기능이 없어서 DB에 남기지 않습니다.
- STOMP over WebSocket, 내장 Simple Broker를 사용합니다. 메시지 형식은 [API_CONVENTION.md](./API_CONVENTION.md)를 따릅니다.
- 승객은 **좌석 번호**로 표시합니다 (자유 이동 없음).
- 대기실에서는 **호칭만** 씁니다. 계정 닉네임은 절대 내보내지 않습니다.
- **방송 문장 형식**: `안내 말씀 드립니다. {호칭}님은 지금 '{상황 칩}'입니다.`
  - 예: 안내 말씀 드립니다. 104번 두근두근한 양님은 지금 '답장 기다리는 중'입니다.
  - 상태 칩은 호칭에 이미 들어가서 문장에 따로 넣지 않습니다.
  - 방송할 때 상태 칩은 필수라서 (BR-01), 방송 문장의 호칭에는 항상 상태 칩이 있습니다.

## 7. 서버 자원 원칙

서버 한 대, 작은 인스턴스를 전제로 합니다.

1. Redis, 별도 메시지 브로커를 쓰지 않습니다.
2. 바뀌지 않는 데이터(방, 칩, 도안)는 메모리에 올려 두고 씁니다.
3. 반복되는 사용자 행동(탭, 클릭)마다 API를 부르지 않습니다. 모아서 한 번에 보냅니다.
4. 시간이 지나서 생기는 값(열차, 털실)은 스케줄러로 만들지 않고 계산합니다.
5. 다시 읽지 않는 데이터(방송, 리액션)는 DB에 쓰지 않습니다.
