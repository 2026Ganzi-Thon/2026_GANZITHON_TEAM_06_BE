# 도메인 설계

> 기준: 노션 기능명세서(각 파트 공유 내용 정리 → 기능 명세서), 아이디어 구체화 문서
> 새 기능을 만들기 전에 **이 문서에서 어느 도메인에 속하는지** 먼저 확인하세요.

## 1. 서비스 한 줄 요약

내가 바꿀 수 없는 기다림(합격 발표, 답장)을 **2D 간이역 대기실에서 다른 승객과 함께 보내는 서비스**입니다.
사용자는 승차권을 받고 대기실에 앉아 있다가, 열차가 지날 때마다 털실을 받고, 기다림이 끝나면 담요 조각 1칸을 받습니다.

```
입구 → 대기실 선택 → 상태 칩 선택 → 승차권 발급 → 자동 착석
→ 함께 기다리기 (열차가 지날 때마다 털실, 털실 톡톡은 선택)
→ 기다림 종료 → 담요 조각 선물 → 저장 → 마이 양의 내 담요
```

## 2. 도메인 한눈에 보기

| 패키지 | 한글 이름 | 맡는 것 | 저장 |
|---|---|---|---|
| `user` | 사용자 | 게스트 토큰 발급, 닉네임 간이 로그인, 담요 공개 설정 | DB |
| `room` | 대기실 정보 | 방 목록, 슬로건·문구, 상황 칩, NPC, 가상 승객, 도안 | DB (시드 데이터, 시작 시 메모리에 로드) |
| `ticket` | 승차권 | 기다림 한 건의 시작부터 종료까지, 열차·털실 계산, 털실 톡톡, 전광판 통계 | DB |
| `blanket` | 담요 | 담요 조각, 내 담요, 임시 보관, 계정으로 옮기기, 공개 카드 | DB |
| `realtime` | 실시간 대기실 | 접속 승객, 좌석, 존재감, 방송, 리액션, 전광판 송출 | **메모리만** |
| `global` | 공통 | 설정, 보안, 예외, 공통 응답 | — |

### 관계

```
room ─── 1:N ─── ticket ─── 1:1 ─── knitting (ticket 안에 포함)
                   │
user ─── 1:N ──────┤
                   │
                   └─── 1:0..1 ─── blanketPiece ─── N:1 ─── user

realtime: DB 관계 없음. 접속 중인 승객을 ticket 기준으로 메모리에 들고 있음
```

### 서비스 호출 방향

```
realtime ──→ ticket ──→ blanket
   │            │
   └──→ room ←──┘          user ←── ticket, blanket (소유자 확인)
```

- 화살표 반대 방향으로는 호출하지 않습니다 (순환 참조 금지).
- 예: 기다림 종료는 `TicketService.end()`가 `BlanketService.createPiece()`를 호출합니다. blanket이 ticket을 호출하지 않습니다.

## 3. 용어집

**한 개념에는 한 단어만 씁니다.** 클래스, 변수, API 경로 모두 이 표를 따릅니다.

| 명세서 용어 | 코드 이름 | 설명 |
|---|---|---|
| 승차권, 기다림 | `Ticket` | 둘 다 Ticket입니다. `Waiting`은 쓰지 않습니다 |
| 승차권 번호 | `ticketNumber` | "104번 양"의 104 |
| 대기실(방) | `Room` | 결과발표 / 읽씹 / 결선 |
| 상황 칩 | `SituationChip` | 방마다 다름 |
| 상태 칩 | `MoodChip` | 공통 12개. `StatusChip`은 `TicketStatus`와 헷갈려서 쓰지 않습니다 |
| 열차 | `Train` | 1시간마다 지나감. 저장하지 않고 계산 |
| 털실 한 올 | `Yarn` | 열차 1대 = 털실 1올. 저장하지 않고 계산 |
| 털실 톡톡 | `Knitting` | 탭으로 도안을 채우는 미니 콘텐츠 |
| 도안 | `Pattern` | 조각의 무늬 |
| 담요 조각 | `BlanketPiece` | `Piece`만 쓰지 않습니다 |
| 종료 사유 | `EndReason` | `ANSWERED` 답이 왔어요 / `UNEXPECTED` 기대와 달랐어요 / `LET_GO` 내려놓을래요 |
| 방송 | `Broadcast` | 상황 칩 + 상태 칩 조합 |
| 리액션 | `Reaction` | `NOD` 끄덕임 / `AWW` 짠함 |
| 승객 | `Passenger` | 지금 대기실에 접속한 양. `realtime`에서만 사용 |
| 가상 승객 | `VirtualPassenger` | 시연용으로 자동 방송하는 승객 |
| NPC | `Npc` | 방마다 1명, 조용히 앉아만 있음. 방송·리액션 불참 |
| 사용자 | `User` | 게스트 또는 닉네임 로그인 사용자 |

## 4. 도메인별 상세

### 4-1. `user` 사용자

| 기능 ID | 내용 |
|---|---|
| ON-01 | 첫 진입 시 게스트 사용자 생성 + 토큰 발급 (로그인 없이 시작) |
| MY-01 | 닉네임 + PIN(숫자 4자리) 간이 로그인 |
| MY-04 | 담요 공개 설정 (기본 비공개, 로그인 사용자만) |
| SV-01 | 로그인 상태 판별 |

- 주요 데이터: `User` (닉네임, PIN 해시, 공개 여부, 게스트 여부)
- **게스트도 사용자입니다.** 처음 들어오면 게스트 `User`를 만들고 토큰을 줍니다. 그래서 승차권과 담요 조각에는 **항상 소유자가 있습니다.**
- 닉네임 로그인 시
  - 처음 가입: 지금 게스트 사용자에 닉네임과 PIN을 채웁니다. 모은 조각이 그대로 계정 조각이 됩니다.
  - 이미 계정이 있음: 게스트가 가진 조각을 기존 계정으로 옮깁니다.
- "임시 보관 조각" = **아직 게스트 사용자 소유인 조각**입니다. 따로 구분하는 필드가 없습니다.
- 닉네임은 중복 불가. PIN은 `PasswordEncoder`로 **해시해서 저장**하고, **틀린 횟수를 제한**합니다 (예: 5번 실패 시 잠시 잠금).
- 토큰 발급·검증과 "현재 사용자 꺼내기"는 `global/security`가 맡고, `user`는 그걸 가져다 씁니다.
- 다른 도메인은 "이 요청을 보낸 사람이 누구인가"를 `user`를 통해 확인합니다.

### 4-2. `room` 대기실 정보

| 기능 ID | 내용 |
|---|---|
| ON-02 | 대기실 목록 |
| RM-01 | 방 슬로건·문구 (입장, 열차 통과, 종료 3종, 회고 질문 2개) |
| RM-03, RM-04 | NPC 정보, 공감 문구(P1) |
| RM-05 | 가상 승객 정의 |
| YT-01 | 도안 목록 (랜덤 배정용) |
| SF-02 | 칩 목록 고정 (자유 입력 없음) |

- 주요 데이터: `Room`, `SituationChip`, `Npc`, `VirtualPassenger`, `Pattern`
- `MoodChip`(상태 칩 12개)은 모든 방 공통이라 **enum**으로 둡니다.
- 대기실은 결과발표 / 읽씹 / **간지톤 결선** 3개입니다.
- 사용자가 바꾸는 데이터가 아닙니다. 시드 데이터로 넣고 서버 시작 시 메모리에 올려서 요청마다 DB를 조회하지 않습니다.

### 4-3. `ticket` 승차권 (중심 도메인)

| 기능 ID | 내용 |
|---|---|
| ON-03, ON-04 | 상태 칩 선택(선택 사항), 승차권 발급 |
| TR-02, TR-04 | 털실 지급, 지나간 열차 수 |
| YT-03, YT-04, YT-05 | 털실 톡톡 진행, 역장에게 전달, 미참여 시 기본 조각 |
| EN-01 ~ EN-03 | 내려놓기, 종료 사유 선택, 회고 질문 |
| BR-04 | 전광판 "도착 N건 / 내려놓음 N건" 집계 |

- 주요 데이터: `Ticket` (승차권 번호, 방, 소유자, 상태 칩, 상태, 시작·종료 시각, 종료 사유), `Knitting` (도안, 톡 횟수, 전달 시각)
- 상태: `WAITING` → `ENDED`. **이어서 재개는 없습니다.** 다시 기다리려면 새 Ticket을 만듭니다.
- **승차권 번호는 대기실마다 1번부터 순번**으로 매기고 리셋하지 않습니다. 예: 결과발표 방 104번 양
- **저장하지 않고 계산하는 값**
  - 지나간 열차 수 = (종료 시각 또는 현재 - 시작 시각) × 가속 배율 ÷ 1시간
  - 털실 수 = 지나간 열차 수
  - 1시간을 몇 초로 줄일지는 **환경변수**로 둡니다 (기본값: 1시간 = 15초). 첫 열차는 입장 10초 안에 지나가게 합니다
- 털실 톡톡의 톡 횟수는 **탭할 때마다 받지 않습니다.** 프론트가 모아서 "전달"이나 종료 때 한 번에 보내고, 서버는 도안 칸 수를 넘지 않는지만 검사합니다.
- 전광판 통계는 **종료 사유 3가지를 각각** 세서 내려줍니다 (`ANSWERED`, `UNEXPECTED`, `LET_GO`). 화면에 어떻게 묶어 보여 줄지는 프론트가 정합니다.
- 통계는 **전체 합산만** 제공합니다 (방 단위 통계 없음). 종료 때마다 메모리 카운터를 올리고, 서버 시작 시에만 DB에서 집계합니다.
- 회고 질문 답변(EN-03)은 **저장하지 않습니다** (다시 보여 주는 곳이 없음). 기획 답에 따라 바뀔 수 있습니다.

### 4-4. `blanket` 담요

| 기능 ID | 내용 |
|---|---|
| EN-04, EN-05 | 담요 조각 생성, 뒷면 기록 층 |
| SV-02 ~ SV-05 | 계정 저장 / 임시 보관 / 저장 완료 |
| MY-02, MY-03 | 내 담요, 조각 상세 (앞면·뒷면) |
| MY-05 | 대기실에서 승객 탭 시 공개 카드 |
| MY-08 | 임시 보관 조각을 계정으로 옮기기 |

- 주요 데이터: `BlanketPiece` (Ticket 1:1, 소유자, 도안, 뒷면 기록 층)
- **뒷면 기록 층**(승차권 번호, 기다림 이름, 지나간 열차 수, 종료 표식)은 조각을 만들 때 값을 복사해 두고 **이후에 바꾸지 않습니다.**
- **기다림 이름** = 마지막으로 방송한 상황 칩의 문구. 방송을 한 번도 안 했으면 방 이름.
- 종료 사유와 관계없이 **조각은 항상 1칸**입니다.
- 공개 카드에는 **종료 표식을 넣지 않습니다** (민감 정보는 본인만).

### 4-5. `realtime` 실시간 대기실

| 기능 ID | 내용 |
|---|---|
| ON-05 | 자동 착석 (좌석 배정) |
| RM-02 | 존재감 표시 (머문 시간, 상태 칩) |
| BR-01 | 조합형 방송 (30초 쿨다운) |
| BR-02 | 전광판 송출 (15초 노출, 순서대로 전환) |
| BR-03 | 1초 리액션 (즉시 전파, 알림 없음) |
| RM-05 | 가상 승객 자동 방송 (스케줄러) |

- **DB에 저장하지 않습니다.** 접속 승객, 좌석, 방송 대기열, 쿨다운 모두 메모리에 있습니다. 서버를 재시작하면 사라지고, 다시 접속하면 복구됩니다.
- 방송·리액션은 다시 조회하는 기능이 없어서 DB에 남기지 않습니다.
- STOMP over WebSocket, 내장 Simple Broker를 사용합니다. 메시지 형식은 [API_CONVENTION.md](./API_CONVENTION.md)를 따릅니다.
- 승객은 **좌석 번호**로 표시합니다 (자유 이동 없음).

## 7. 서버 자원 원칙

서버 한 대, 작은 인스턴스를 전제로 합니다.

1. Redis, 별도 메시지 브로커를 쓰지 않습니다.
2. 바뀌지 않는 데이터(방, 칩, 도안)는 메모리에 올려 두고 씁니다.
3. 반복되는 사용자 행동(탭, 클릭)마다 API를 부르지 않습니다. 모아서 한 번에 보냅니다.
4. 시간이 지나서 생기는 값(열차, 털실)은 스케줄러로 만들지 않고 계산합니다.
5. 다시 읽지 않는 데이터(방송, 리액션)는 DB에 쓰지 않습니다.

## 8. 확인 필요 (기획)

| 항목 | 내용 | 정해지기 전 처리 |
|---|---|---|
| 플레이어 이동 | MVP에 넣을지 | 넣지 않음 (자동 착석만) |
| 회고 질문 | 질문 내용, 답하는 방식, 다시 보여 주는 곳이 있는지 | 저장하지 않음 |
| 시드 데이터 | 방 문구, 상황·상태 칩 확정본, NPC, 가상 승객, 도안 개수와 칸 수 | 아이디어 문서 기준 임시 데이터 |
